# Оптимизация tvOS Launcher: аудит и два языка

Дата: 12 ноября 2026. База сравнения: `fb0e6f0` (2.1.5-ru.1).
Проверка выполнена по подходам Matt Pocock `codebase-design` и `diagnosing-bugs`:
отдельно воспроизводимые результаты и наблюдения по коду, без оценки FPS по настольным тестам.
Проверку на X4Q Pro пользователь отложил; запуск, CPU/PSS и плавность на приставке не измерялись.

## Выполненная оптимизация: русский и английский

- В интерфейсе, настройках и определении локали осталось два языка.
- Все 1233 русских перевода и 38 английских символьных ключей сохранены без изменения значений.
- Удалены 1428 ненужных аргументов перевода из вызовов, остальные словари и турецкие ресурсы,
  документация и скриншоты. Страны контента и имена футбольных команд сохранены.
- Вместо нескольких языковых словарей используется один русский; английский текст служит ключом.
- Поиск получил русскую и английскую клавиатуры вместо английской, турецкой и хинди;
  дополнительный язык голосового ввода также русский/английский.
- Убрана постоянная смена приветствия на иностранных языках в мастере настройки.
- Сохранены ключи настроек. Если ранее выбран удалённый язык, при первом чтении выбирается
  русский для русской системной локали либо английский для остальных.

## Приоритетные находки в остальном проекте

### 1. Частый фоновый опрос ради исправления громкости

`PowerService.startAudioDumpVolumeWatcher` создаёт новый `audio-dump-writer` и выполняет полный
Binder dump AudioService на каждой итерации. После неё пауза составляет 60 мс в стандартном режиме
или 35 мс в режиме Onn, даже когда кнопка отпущена. Длительность самого dump добавляется к паузе.
Это верхняя оценка около 17/29 итераций в секунду, не измеренный расход CPU.

Условия: служба специальных возможностей включена, исправление громкости включено,
выдано DUMP, экран активен, альтернативный ADB-поток не перехватил обработку.
Исправление громкости по умолчанию включено. Удержание в режиме Onn дополнительно запускает
опрос состояния ввода с паузой 10 мс; это отдельный сценарий.

Предлагаемый следующий шаг: на X4Q сравнить CPU/потоки при включённом и выключенном исправлении,
проверить необходимость обходного пути и использовать быстрый опрос только на время удержания.
Сначала нужен замер на устройстве, чтобы сохранить корректную работу кнопок.

Ссылки: `src/com/techgenius/tvoslauncher/PowerService.java`, методы
`startAudioDumpVolumeWatcher`, `checkHardwareKeyDownState`, `syncVolumeHoldFix`.

### 2. Неограниченные кэши собственных обоев

`CustomMedia.cachedSceneWalls`, `cachedClassicWalls`, `ICON_CACHE` — статические HashMap без
лимита размера. При добавлении/просмотре новых обоев битмапы остаются в этих картах.
`MainActivity.onTrimMemory` очищает часть кэша SceneView, но не эти статические карты.
`LoadedScene.ownsBg=false` для пользовательских сцен также оставляет изображение владельцу CustomMedia.

Расчёт для ARGB_8888: одно изображение 1920×1080 занимает примерно 7.91 МиБ пикселей;
20 разных таких обоев — примерно 158.2 МиБ только в этом кэше. Это расчёт по размерам,
а не фактический PSS. Дополнительные буферы и GPU-ресурсы сюда не включены.

Предлагаемый следующий шаг: один модуль хранения изображений с лимитом по байтам, учётом активного
и переходного фона и обработкой onTrimMemory. Владение битмапами должно быть явным: нельзя вызывать
recycle у изображения, которое ещё используется View или анимацией.

Ссылки: `CustomMedia.java`: поля кэша, `setCustomSceneWallpaper`, `getCustomSceneWallpaper`;
`Scenes.java`: `LoadedScene.recycle`; `MainActivity.java`: `onTrimMemory`.

### 3. Декодирование и подготовка сцен могут блокировать интерфейс

`SceneView.onDraw` вызывает `ensureLoaded`. На промахе кэша тот читает и декодирует изображения,
подготавливает стеклянные текстуры. `advanceScene` также вызывает его из Handler главного потока.
Поэтому холодная смена сцены может выполнять тяжёлую работу перед кадром.
В стартовом `MainActivity.onCreate` дополнительно есть ожидание `appsTask.get()` в UI-потоке:
фоновая загрузка приложений остаётся частью критического пути первого кадра.

Предлагаемый следующий шаг: подготовка следующей сцены в фоне, применение результата по идентификатору
поколения, чтобы устаревший результат не заменял выбранную сцену; отрисовка только готовых данных.
Для запуска — замер участка ожидания и возможность показать оболочку до завершения списка приложений.
Сам факт синхронного пути подтверждён кодом, длительность задержки на X4Q пока неизвестна.

### 4. Повторные запросы виджета не объединяются

`HomeDashboard.fetchLatestReleases` проверяет готовый кэш, но не запрос, который ещё выполняется.
`EXEC` — cached thread pool. На холодном/просроченном кэше несколько вызовов для одинаковой
локали и стран запускают отдельные работы. В запросах футбола и намаза аналогичная структура;
для них отдельный стенд не запускался.

Воспроизведён вызов реального `fetchLatestReleases` с задержанной заглушкой транспорта:

```text
calls=20 force=false cache=empty identical_country_sets=1 transport_requests=20
AssertionError: Expected one in-flight fetch per signature; actual=20
```

Это настольный тест планирования запросов, без реального Android UI и без обращений в сеть.
В fixtures заменены Context/Handler/TextUtils и транспорт Suggestions; сама логика
HomeDashboard взята из собранного проекта. Результат не зависит от скорости внешнего API.
Диагностическая проверка намеренно завершается ошибкой, пока объединение запросов не реализовано;
она отделена от обычных проверок LauncherChecks.

```sh
mkdir -p build/request-probe
javac -encoding UTF-8 --release 11 -cp "build/classes:$SDK/platforms/android-34/android.jar" \
  -d build/request-probe $(find tests/performance-fixtures -name '*.java')
java -cp "build/request-probe:build/classes:$SDK/platforms/android-34/android.jar" \
  com.techgenius.tvoslauncher.DashboardRequestProbe
```

Предлагаемый следующий шаг: один выполняющийся запрос на ключ, список ожидающих результатов,
ограниченный пул работ, задержка повторения после ошибки. По codebase-design это отдельный модуль
получения данных: создание карточек не должно определять число сетевых работ.

## Что уже ограничивает лишнюю работу

- MainActivity.onPause останавливает таймеры видимой части Home и ротацию сцен.
- Неанимированный кадр сцены кэшируется; часы инвалидируются при изменении подписи времени.
- Поиск использует задержку 350 мс и LRU-кэш с бюджетом по байтам.
- Для изображений уже используется inSampleSize; часть загрузки выполняется в фоне.

## План проверки на X4Q после подключения

1. Холодный запуск и первый кадр: 10 запусков, p50/p95 и trace участка appsTask.get.
2. 60 секунд простоя: CPU, число потоков и пробуждения с исправлением громкости и без него.
3. Смена 20 собственных обоев: PSS до/после, onTrimMemory и возврат из другого приложения.
4. Смена встроенной/USB-сцены: frame times, декодирование и стеклянные текстуры в trace.
5. Медленная/отключённая сеть: быстрые переходы между приложениями и виджетами, число запросов.
